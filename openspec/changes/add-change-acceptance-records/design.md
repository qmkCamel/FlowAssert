## Context

基线为 `REDACTED_REVISION`，不是原工作区尚未更新的 `dev`。已有 `workbench-contracts.ts` 提供来源和五维投影，`workbench-investigation.ts` 提供父子运行核查，`workbench-references.ts` 提供通用 v3 消费者引用。现有运行中的提交与构建信息可能来自声明，不能直接当作制品供应链证明。动机见 [proposal.md](proposal.md)。

## Goals / Non-Goals

目标：形成从变更范围、运行选择、证据核对到 PR 摘要的完整本机闭环，允许非作者识别已验证、未验证、失败和恢复；同一修订在所有出口产生相同结论。

非目标：自动发现 PR、抓取仓库私有信息、构建或安装 App、验证签名供应链、自动提交 GitHub 评论／检查状态、替团队决定业务覆盖充分性。用户填写的场景仍是声明的验收范围。

## Decisions

### 1. 验收是独立对象，不修改运行历史

新增 `workbench-change-contracts.ts`、`workbench-change-acceptance.ts` 和独立存储模块；由 `WorkbenchApplication.acceptanceRecords` 组装。既有首次验收助手 `workbench-acceptance.ts` 不承担持久化聚合职责。

放弃“给每个 TestRun 加 PR 字段即可”的方案：一个变更通常有多个场景、多个平台和多次失败，需要多对多关系与独立修订。也不把整个清单复制进每个运行。

| 对象 | 关键内容 | 约束 |
| --- | --- | --- |
| 变更身份 | 本机 UUID、仓库公开标签、完整提交摘要、可选 PR 正整数 | 不接受任意 URL／本机仓库路径；提交为 40 或 64 位十六进制，旧运行短摘要只作线索 |
| 制品声明 | App ID、平台、二进制 SHA-256、构建标签、来源与声明时间 | 没有设备可观测摘要时显示“声明”，不得标成 observed |
| 覆盖单元 | 场景 ID、说明、平台／环境槽位、所需验证维度、制品引用 | 1–100 个单元，ID 唯一，发布后冻结，不能靠删除失败单元刷新旧修订 |
| 材料引用 | 类型、来源 ID、运行／记录 ID、清单摘要、选择理由 | 首期 native-run；外部结果和矩阵用后续明确类型扩展，未知类型拒绝 |
| 修订 | 序号、上版摘要、输入摘要、政策版本、生成时间、覆盖表、缺口 | 只增不改；每对象最多 100 修订，每版清单不超过 4 MiB |
| 当前核查 | 核查时间、材料可用性、当前有效结论 | 与生成时快照分离，损坏不能继续显示绿色 |

每个覆盖单元可绑定一条选定验收链；可保留多个历史失败，但必须明确哪条链满足哪项要求。禁止通过相同用例名称猜关联，禁止把不同 App、参数、平台或场景的 UI 与业务结果拼成一次通过。

### 2. 冻结范围与严格聚合

`preview(input)` 在读租约下读取已完成的原生运行及证据，复用投影，计算输入摘要、核查时间和缺口；`publish(previewDigest, expectedRevision)` 再读并比对所有来源，原子创建新修订。预览过期或并发版本变化返回冲突；无隐式覆盖。

严格通过条件：

1. 每个声明覆盖单元都有明确选定的原生运行；所有强制维度满足且当前证据完整。
2. App／平台／完整提交／制品绑定相符。声明型来源要求用户显式确认，并在摘要保留“声明关联，未验证供应链”的限制；缺失或冲突仍阻断通过，人工说明不能消除冲突。
3. 选定链没有未解决失败、恢复或清理缺口。`recovered` 不自动转为干净通过；若存在独立干净复验，需显式关联，原失败仍展示，摘要称“复验通过”，不称首次通过。
4. 旧提交上的失败可作为修复背景，但不能覆盖新提交；新提交仍须在冻结范围逐项验证。复跑变化依据已有调查服务显示，不能声称一次复验证明根因。

聚合返回 `pass / fail / incomplete / cancelled`，同时返回全部原因；确定失败优先于 incomplete，incomplete 优先于纯 cancelled。CLI 退出码依次为 0、1、2、130。零场景、零结果、进行中、材料缺失、导入未复验、来源不匹配均不能为 0。按同一纯函数生成 Viewer、JSON、Markdown 和 Agent 摘要。

### 3. 引用提交协议和当前完整性

在 store 下新增 `acceptance/`。持久化前通过容量准入，保留既有 256 MiB 余量；未知容量拒绝。读操作持有来源读租约，复制投影而不是修改原 manifest。

发布顺序：持久化意图记录 → 在 mutation gate 内重验来源 → 发布 v3 `acceptance:revision` 引用 → 不可覆盖发布修订 → 原子更新索引 → 完成意图。引用在修订前发布，崩溃最多多保护材料，不能让成功修订引用已清理材料。重启根据意图恢复或标记 interrupted；不能因重试创建另一份成功修订。引用数量超过既有单记录上限时拆分，并在同一意图登记。

废弃对象先写 tombstone，再撤销本对象引用；保留摘要和历史结论，不顺带删除运行。重复发布相同请求键和摘要返回原修订，不同摘要冲突。未知引用版本、损坏意图或索引时失败关闭，不继续清理相关材料。

下载和新核查重新验证清单及材料摘要。不可变的“当时结论”保留，当前有效结论可以降为 incomplete；不偷偷改写先前发布的 JSON。离线 Markdown 标记生成时间与“材料此后可能变化”，不得宣称实时可用。

### 4. 服务边界与用户入口

| 入口 | 拟定协议 | 权限与限制 |
| --- | --- | --- |
| 预览 | POST `/api/workbench/acceptance-records/preview` | 同源，最多 1 MiB 输入，不执行设备动作 |
| 发布 | POST `/api/workbench/acceptance-records` | 显式确认、预览摘要和期望版本，返回 job ID |
| 查询 | GET `/api/workbench/acceptance-records/:id` | 有界分页，旧快照及当前核查分开 |
| 下载 | GET `/api/workbench/acceptance-records/:id/revisions/:revision/export?format=json或markdown` | 只导出固定安全字段，附件另走原分享流程 |
| CLI | `acceptance preview/publish/show/export` | 连接已显式登记本机 runtime，不自行启动或猜测设备 |
| Agent | 新增只读 `mobile_acceptance_get` | DSH 注册表与 MCP 共用命令契约，必须显式 ID，输出有界元数据 |

使用 `SourceResolver` 内部接口隔离类型：输入是受验证来源 ID，输出是冻结投影、摘要、材料引用与读租约；不接收任意文件路径，也不允许 adapter 判定整个变更通过。第四项只注册本机运行解析器，第五／六项按新类型接入，不在第四项添加虚假外部实现。

长操作使用独立任务契约，不修改旧任务枚举的含义；状态为 accepted/running/committing/finished/cancelling/interrupted。客户端取消只在提交前生效；提交后返回已完成修订，不给出模糊的“取消成功”。新只读 Agent 工具不提供创建／发布授权，现有 17 个工具保持参数及语义兼容，工具总数的增加必须更新测试与文档。

### 5. 摘要的安全边界

摘要仅包含公开标签、摘要、覆盖维度、结果、运行标识和明确缺口。运行原始错误、YAML、参数、设备序列号、绝对路径、终端输出、截图及业务返回值均不自动进入导出。Markdown 转义控制字符、HTML、表格和链接语法，恶意场景名不得制造可点击 URL 或执行脚本。图片外发仍需原分享预览和授权，本功能不代替脱敏。

Viewer 用独立区域显示生成进度、取消和错误；重复提交禁用，但历史切换、语言切换、设备只读预览继续可用。新失败保留旧修订；切换对象用请求身份与 AbortController 防止迟到响应污染。完成时间来自领域事件，不取渲染时间。

### 6. 验证与交付标准

- 契约／纯函数：完整通过、维度缺口、跨提交／制品冲突、复验、恢复、混合平台、零覆盖、恶意标签和出口一致性。
- 存储：重复请求、过期预览、容量未知／不足、发布切点 SIGKILL、引用竞争、损坏／缺失材料、撤销幂等及重启；断言没有修改原运行字节。
- 浏览器：真实服务＋Mock 运行，生成过程中切换另一控件，失败保留旧修订，下载实际文件，宽窄屏截图留存并人工检查。
- 包与宿主：同一 tarball 的 CLI、MCP、DSH `0.1.5-rc.2` Native/PTC，检查新增只读工具与原工具权限；不使用全局其他版本代替验证。
- 外部验收：一项真实业务代码变更、对应 Android/iPhone 构建和独立业务核查；至少两位非作者根据摘要复核来源与缺口。未提供这些材料可继续工程测试，不可勾掉外部验收。

## Risks / Trade-offs

- 声明提交可能不对应设备包 → 显示来源等级并要求显式确认；不宣称供应链验证。
- 严格门禁可能让大量旧记录不完整 → 原历史不迁移，不“补写”未知来源，允许查看但不算验收通过。
- 引用保护会增加磁盘占用 → 显式废弃／撤销，加上容量准入，不能后台删证据解围。
- 评审摘要不是自动覆盖证明 → 显示要求范围和未覆盖项，不生成“所有需求均已验证”的泛化语句。

## Migration Plan

先落契约与只读服务，再持久化和故障测试，最后接 Viewer／CLI／宿主。功能通过显式入口启用，不改变旧 YAML。回滚代码时保留新目录及引用；旧版本不认识新对象只能拒绝读取，不能删除。每阶段独立提交并记录实际门禁；本方案阶段不提交功能完成声明、不归档。
