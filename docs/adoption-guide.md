# FlowAssert 采用指南与适用性评估

修复闭环为 **Preview（预览能力，默认关闭）**，只适合受控项目试用。M1/M2 软件验证与 M3 Mock 安装协议不等于真实 App 修复验收；项目 `repair.enabled` 与宿主 `repairToolsEnabled` 分开控制，尚无统一总开关或 Viewer 一键开关。使用范围、审批与停用见[修复指南](evidence-guided-repair-operations.md)。

初版：2026-09-18；2026-10-07 按 `dev@REDACTED_REVISION` 核对当前入口与边界。本文帮助团队判断是否采用 FlowAssert、应从哪一层开始，以及什么证据才足以进入稳定回归。具体能力状态以[能力总表](capabilities.md)为准，架构边界以 [ADR](decisions/) 和主规格为准。

发布前/升级前先看[版本与归档兼容边界及脱敏问题报告指南](workbench-compatibility.md)与[安装指南](beta-installation.md)；当前开发包的能力不能外推到已发布的 alpha.1。报告阅读和离线交接见[报告指南](report-reading-and-sharing.md)，有界时间/重启/业务与性能断言见[运行时指南](runtime-assertions.md)。这些工程能力不替代外部试点、健康来源和独立用户验收。

## 1. 先回答四个核心问题

| 采用问题 | 当前答案 | 适用条件 | 不能据此承诺什么 |
| --- | --- | --- | --- |
| 能否在电脑上准实时看到连接的手机？ | 可以。独立 Viewer 已支持 Android scrcpy、iOS WDA MJPEG，并在连续媒体不可用时退化为截图轮询 | macOS 本机、USB 或已配置连接、Android 调试授权或 iOS 信任/WDA 签名已完成 | 不代表所有 OEM、系统版本、旋转、断线恢复、音频和远程设备均已验证 |
| 能否用可读流程快速重复人的手动操作？ | 可以。当前默认是 AppClaw YAML + MirrorService/Appium，支持点击、滑动、等待、公开文字输入、断言、参数、子流程、条件、循环和串行套件 | 页面可由 accessibility tree 或受控坐标稳定识别，测试数据和账号状态可重置 | 不承诺任意页面自动生成稳定用例，也不把模型探索等同于确定性回归 |
| 能否保留证据并替代人工确认结果？ | 可以替代已明确声明的 UI 条件和业务真值检查。每步保存 PNG/XML、时间窗和哈希，可选录像；可信 verifier 可独立读取服务端或测试夹具状态 | 必须先定义通过条件、必需证据和独立业务 verifier；证据缺失、清理失败或结果不确定不能判 pass | 仅看到成功提示不能证明业务成功；未配置 verifier 时业务验证明确为 `not-performed`；未知视觉遮挡尚无通用门禁 |
| 测试结果能否回溯和比较？ | 可以。runId 关联输入快照、步骤证据、日志、录像、case/attempt、JSON/JUnit、报告目录、跨次比较和 Diagnostic Context | 运行材料可持久化且未被人工删除；共享材料时遵守本机证据权限 | 不内置 AI 根因或 AI verdict；当前比较是确定性事实整理，不是统计性能回归平台 |

如果团队需要的正是以上四项，并接受明确的设备矩阵和验收边界，FlowAssert 适合作为本机双端真机回归工作台。若主要目标是云端多设备并发、无障碍树完全不可用的视觉自动化，或直接复用大规模既有 Maestro 用例库，应先做专项评估。

## 2. 哪些团队适合采用

### 适合直接试点

- 自研 Android/iOS App，需要在开发机连接真机做高频固定回归；
- 希望用 YAML 让测试、研发和 Agent 共同维护流程，少量复杂判断允许使用登记代码扩展；
- 对失败现场、输入快照、证据哈希、业务真值和清理结果有明确审计要求；
- 已有 Appium/WDA/ADB 基础，能够准备稳定账号、测试环境和可清理的数据；
- 希望 Viewer、CLI、MCP/Codex 和 DeepSeek Harness 共用同一套确定性执行与证据结果。

### 需要先做受控 PoC

- 页面大量使用自绘控件、游戏画布、视频画面或动态坐标，accessibility tree 信息不足；
- 依赖系统权限弹窗、跨 App、锁屏、旋转、断线重连或特定 OEM 行为；
- 业务验证需要访问内部 API、数据库或复杂凭据；
- 希望将有限 AI 恢复作为必需门禁，而不是确定性流程失败后的受控补救；
- 需要在 CI 主机长期运行，且设备签名、USB 稳定性和资源清理尚未形成基线。

### 当前不适合作为唯一方案

- 核心诉求是云设备农场、大规模多设备调度或跨地域共享 daemon；本机双槽矩阵已有工程实现，真实双槽验收仍待补；
- 要求通过截图自动判断任意未知遮挡、颜色、布局和视觉质量；
- 要求自动操作密码、验证码、支付、密钥或其他敏感输入；
- 要求一个模型自由执行任意代码、任意 YAML 或未经登记的破坏性流程；
- 已有大规模 Maestro 原生 YAML 资产且不能迁移。Maestro fork adapter 当前[已决策后置](decisions/0006-native-yaml-workbench.md#2026-09-18maestro-fork-adapter-暂缓)，此场景应先重新评估 adapter 成本与设备 owner 交接。

## 3. 推荐采用路径

### 阶段 A：先建立“看见并留证”基线

1. 按 [Android 真机](android-real-device.md) 或 [iPhone 真机](ios-real-device.md)完成设备依赖和授权；
2. 启动[独立 Viewer](local-viewer.md)，确认连续画面、截图降级、手动截图和录屏；
3. 固定设备型号、系统版本、连接方式、媒体模式和已知限制；
4. 保存一次可复现的连接与断开记录。

出口条件：画面可用，操作时 Viewer 仍响应，断开只清理本工具拥有的资源。此阶段不声称自动化流程或业务验证已经可用。

### 阶段 B：固化一个确定性 UI 流程

1. 选择 5–15 步、数据可重置、结果明确的高频人工流程；
2. 使用[工作台 YAML](test-workbench.md)表达动作、等待和 UI 断言；
3. 对成功、故意失败、取消和重启历史各跑一轮；
4. 检查每步 PNG/XML、时间窗、哈希和最终 verdict。

出口条件：正例稳定通过，反例在预期步骤失败，材料缺失不会误判为 pass，取消后不会继续派发动作。

### 阶段 C：加入业务真值和清理

1. 为测试环境提供 prepare、verify、cleanup 接口或登记代码扩展；
2. 让 verify 独立读取服务端、数据库或测试夹具状态，不复用 UI 成功提示；
3. 验证业务值错误、接口异常、清理失败和进程中断；
4. 将业务结论、资源 journal 和清理结果写入同一个 run。

出口条件：UI 操作、业务真值和清理都成功才判 pass。参考仓库内[双端业务夹具](business-test-fixture.md)及[可复制的已登记 HTTP 模板](workbench-business-template.md)；模板的本机假服务测试不替代试点接口验收。

### 阶段 D：形成套件和 Agent 入口

1. 用类型参数、子流程、条件/循环和数据行减少重复；
2. 建立单设备串行套件、标签筛选和安全重试；
3. 输出 JSON/JUnit，并用报告目录和跨次比较定位产品失败、设备故障和证据缺失；
4. 需要 Agent 编排时，只开放已登记流程，通过[运行级工具](agent-test-run-control.md)启动、查询、取消和读取有界证据；
5. 需要离线交接时，人工检查遮蔽与完整 HTML 预览，再明确下载；接收者阅读副本不等于重新验证原业务。

出口条件：Viewer、CLI、MCP/Agent 读取同一 run 事实，Agent 的解释不回写测试 verdict，第二进程不能抢占同一设备。

## 4. 用例进入稳定回归前的验收表

| 检查项 | 必须回答的问题 | 放行标准 |
| --- | --- | --- |
| 设备范围 | 哪些型号、系统版本、连接方式实际跑过？ | 只声明实测矩阵；Mock、模拟器和另一台设备不能替代 |
| 定位稳定性 | 关键目标是否有稳定文字、属性或受控坐标？ | 正例和故意定位失败均落在预期步骤 |
| 等待语义 | 页面完成条件是什么，最长等待多久？ | 使用条件等待和有界超时，不靠无限 sleep |
| UI 判定 | 哪些可访问树条件代表 UI 成功？ | 断言绑定当步新鲜 source；旧 observation 不允许继续操作 |
| 业务判定 | 是否需要证明持久化状态真的变化？ | 必选 verifier 独立读取真值；未配置明确标记 not-performed |
| 证据完整性 | 哪些 PNG/XML/日志/录像是必需材料？ | 缺失、哈希不符或写入失败不能 pass |
| 数据清理 | 运行产生了哪些账号、订单或文件？ | cleanup 有界执行并记录结果；失败不能包装成通过 |
| 失败恢复 | 取消、断线、进程退出后会发生什么？ | 不继续派发动作；未知写入封锁后续控制；owned 资源可诊断 |
| 结果回溯 | 能否从报告回到原始运行和步骤证据？ | runId、case/attempt、输入快照和 evidence refs 可解析且哈希通过 |
| 性能预算 | 人工流程多长，自动化目标多长？ | 记录真实样本与分阶段耗时，不用单次最快结果代表稳定性能 |

## 5. 默认技术选择与可替换边界

- 设备控制默认走 MirrorService/Appium provider；同一设备只有一个明确 owner。
- 固定流程默认走 AppClaw 原生 YAML 执行器和受限 facade，不修改 DeepSeek Harness agent loop。
- Android 连续媒体使用 scrcpy，iOS 使用 WDA MJPEG；媒体不进入 DSH/MCP 连续负载。
- 确定性断言、业务 verifier 和证据完整性共同决定结果；AI 只用于有限导航恢复或结果解释。
- Codex、MCP、DSH/PTC 负责发现和编排已登记测试，不成为第二套测试执行器。
- Maestro fork、共享 daemon、通用视觉门禁和云设备网格均不是当前默认路径。本机双槽矩阵需显式登记和独立进程，不能外推为已通过真实多设备矩阵。

相关决策见 [ADR 0001](decisions/0001-appium-core-local-viewer.md)、[ADR 0006](decisions/0006-native-yaml-workbench.md)和 [ADR 0008](decisions/0008-ptc-host-neutral-orchestration.md)。

## 6. 试点结论模板

完成 PoC 后，用下面的格式做采用决定：

```text
结论：采用 / 有条件采用 / 暂不采用
设备范围：
验证流程：
正例与反例：
业务 verifier：已接入 / 不需要 / 待接入
证据完整性：
单次与重复耗时：
已知限制：
进入下一阶段前必须完成：
```

“采用”只覆盖表中声明的设备、流程和判定条件。新增 App、系统版本、敏感能力、视觉门禁或执行器时，需要重新补充对应验收证据。
